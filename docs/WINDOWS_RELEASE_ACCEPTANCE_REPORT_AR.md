## الملخص التنفيذي

استخدمت جهاز Windows 10 Pro الحالي وNode.js `v24.21.0`. لم أفتح قاعدة الإنتاج أو مجلد بيانات المستخدم الخاص بالتطبيق. اختبارات الاستعادة أنشأت قواعد SQLite اصطناعية داخل مجلدات مؤقتة، وأغلقت العمليات المالكة للقواعد قبل تنظيفها. تحققت بعد التشغيل من اختفاء مجلدي الاختبار المؤقتين.

اختبار استعادة Windows الذي يشغل خادم RetailOS الفعلي نجح في حالتيه، بما فيه فشل تثبيت النسخة ثم فشل التراجع وإعادة تشغيل خادم جديد لاسترداد البيانات الأصلية. اختبار إدارة هوية العملية على Windows نجح في 12 حالة، وفشل تشغيله على Linux كان متخطى حسب إعداد الاختبار.

لم أُثبّت NSIS على Windows الأساسي ولم أشغّل المُثبّت؛ لا توجد بيئة Windows Sandbox مؤكدة أو حساب اختبار منفصل في الجلسة. أنشأت Installer و`win-unpacked` من commit الحالي. المُثبّت غير موقّع. محاولة اختبار قبول النسخة المعبأة توقفت بأمان قبل تشغيل التطبيق لأن استعلام Windows CIM رُفض بـ `Access denied` (`0x80041003`).

## الاستعادة ومفاتيحها

- النسخة اليدوية المشفرة تقبل عبارة مرور يختارها المالك؛ مسار فك التشفير يستخدم العبارة المقدمة إلى `/api/backups/restore` (`apps/web/server.mjs:5380-5415`). يلزم نقل العبارة بشكل آمن مع ملف النسخة.
- للنسخ اليومية، يوجد مسار تصدير يتطلب إذن النسخ، دور OWNER، وإعادة إدخال كلمة مرور الحساب (`apps/web/server.mjs:5137-5175`). يعرض المفتاح الحالي والمفاتيح التاريخية. واجهة المستخدم توضح استخدامها على جهاز جديد (`apps/web/public/app.js:7771-7815`).
- على الجهاز الأصلي، تحفظ نسخة Electron المفتاح اليومي في DPAPI عبر `daily-backup.bin` وسجل المفاتيح في `daily-backup-keyring.bin` (`apps/desktop/src/runtime.ts:297-315`, `338-363`). لذلك نسخة DPAPI المحلية وحدها لا تكفي على جهاز آخر؛ يجب تصدير المفتاح الحالي وأي مفاتيح سابقة والاحتفاظ بها خارج الجهاز قبل فقدانه أو تغيير العبارة.
- يستخدم التطبيق Electron `safeStorage` عبر الواجهات المتزامنة `isEncryptionAvailable`/`encryptString`/`decryptString` (`apps/desktop/src/runtime.ts:168-170` وما بعدها)، ولا يحدد بنفسه علم DPAPI `CRYPTPROTECT_LOCAL_MACHINE`. توثيق Electron يصف حماية Windows بأنها مرتبطة ببيانات دخول المستخدم نفسه؛ وتوضح Microsoft أن `CRYPTPROTECT_LOCAL_MACHINE` يسمح لأي مستخدم على **نفس الجهاز** بفك التشفير، ولا يوفر نقلًا بين الأجهزة. لذلك تغيير النطاق إلى LocalMachine لن يحل الاستعادة بين الأجهزة وسيضعف عزل المستخدمين. [Electron safeStorage](https://www.electronjs.org/docs/latest/api/safe-storage)، [Microsoft CryptProtectData](https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptprotectdata).
- المسار الحالي للاستعادة بين الأجهزة هو عبارة النسخة اليدوية أو مفتاح النسخة اليومية المُصدّر؛ هذا منفصل عن DPAPI ويحافظ على تشفير النسخة AES-GCM. الاختبار الاصطناعي يثبت التوافق البرمجي فقط، لا قبول DPAPI على جهاز آخر.
- **ملاحظة توافق مستقبلية P2:** المشروع يستخدم Electron `45.3.3` (`apps/desktop/package.json:32`) وواجهات `safeStorage` المتزامنة. توثيق Electron الحالي يعلّمها deprecated ويذكر إزالتها في Electron 46؛ يلزم ترحيل منفصل قبل ترقية Electron إلى 46، ولا يؤثر ذلك على البناء الحالي 45.3.3.
- فقدان كلمات المرور/المفاتيح اللازمة يجعل فك النسخ المتوافقة معها غير ممكن عمليًا. لم أختبر تغيير المفتاح على DPAPI حقيقي أو فك نسخة على جهاز Windows ثانٍ.
- لا تضع مفاتيح الاستعادة في رسالة بريد أو ملف غير مشفر. استخدم مدير كلمات مرور موثوقًا أو وسيطًا مشفرًا تحت سيطرة المالك، مع نسخة احتياطية مستقلة.

## العيوب والمخاطر

- **P1 — قبول تشغيل النسخة المعبأة غير مثبت:** اختبار القبول توقف عند CIM `Access denied` قبل تشغيل البرنامج. السبب المثبت هو قيود بيئة Windows الحالية، وليس خللًا في مسار restore. لم أرفع الصلاحيات لتجاوز ذلك؛ يلزم VM اختبار معزول تسمح سياسته بالاستعلام، أو بديل آمن مكافئ يثبت ملكية العملية ورفض PID reuse قبل استخدامه.
- **P1 — Fresh install / upgrade / uninstall / reinstall غير مثبتة:** بُني artifact الحالي لكن لم تُنفذ دورة المُثبّت. يلزم تثبيته في VM أو حساب Windows مخصص ثم إثبات الاحتفاظ ببيانات الاختبار بعد الترقية والإزالة وإعادة التثبيت.
- **P1 — استعادة DPAPI عبر جهاز ثانٍ غير مثبتة عمليًا:** الكود يوفر تصدير المفتاح خارج DPAPI؛ لكن لم يتوفر جهاز ثانٍ للاختبار. يجب اختبار استعادة نسخة يومية باستخدام المفتاح المصدّر على Windows نظيف مستقل قبل اعتبار هذه النقطة مغلقة.
- **P2 — الطابعة وقارئ الباركود غير مختبرين:** لم تظهر طابعة مثبتة في تعداد Windows، ولم يتم إرسال أي مهمة طباعة. لم يُنفذ اختبار جهاز باركود مادي.
- **اختبار CIM مشكلة في بيئة الاختبار، وليس مسار تشغيل التطبيق:** مصدر الاختبار `apps/desktop/scripts/test-packaged-runtime.mjs:150-158` يطلب قائمة عمليات Windows مع PID وPPID والمسار وسطر الأوامر وتاريخ الإنشاء. الجلسة الحالية تعمل بمستوى Medium ومن دون مجموعة Administrators؛ حتى استعلام `Win32_OperatingSystem` واستعلام العملية الحالية رُفضا. اختبار القبول يتوقف fail-closed قبل تشغيل التطبيق. لم أستخدم صلاحيات أعلى.
- `Get-Process` نجح في إظهار قائمة مختصرة لكنه لا يوفر هنا إثباتًا مكافئًا للـ parent PID ووقت الإنشاء وسطر الأوامر. لم أستبدل به فحوص PID reuse أو ملكية العملية. يمكن تقييم Win32 Toolhelp snapshot و`PROCESS_QUERY_LIMITED_INFORMATION` كبديل غير معتمد على CIM، بشرط الحفاظ على نفس إثبات الهوية وإضافة اختبارات خصومية قبل اعتماده؛ لا يوجد بديل آمن مكافئ جاهز ومتحقق منه في المستودع.
- **لا إصلاحات كود في هذه المرحلة.** لم يظهر عيب مؤكد يبرر تعديل التطبيق؛ العائق في بيئة القبول المعزولة، ودورة التثبيت/الجهاز الثاني غير متاحين.

في سيناريو الاستعادة الاصطناعي على Windows، تحقق الاختبار من تطابق snapshot قبل الفشل وبعد بدء الخادم من جديد. تشمل المقارنة الفاتورة وعناصرها، كميات المتغيرات وWAC، حساب 1010، إجماليات Trial Balance، وأرقام القيود. بعد الاستعادة أكد الاختبار `integrity_check = ok`، وعدم وجود مخالفات FK أو قيود يومية يتيمة أو اختلاف جرد أو أرقام فواتير/مفاتيح idempotency مكررة. لم تُستخدم هذه النتائج كدليل على استعادة بين جهازين أو DPAPI.

## المطلوب قبل Pilot

1. وفّر Windows VM أو حساب اختبار منفصل قابلًا لإعادة التهيئة؛ لا تثبّت المُثبّت في حساب المحل. استخدم installer الحالي المبني من commit أعلاه.
2. نفّذ Fresh Install بمالك وبيانات اصطناعية، ثم اختبر المنتج بمتغيراته، والتوريد والبيع والمصروف، وسجّل الفاتورة والمخزون وحساب 1010 والقيود وTrial Balance.
3. أغلق التطبيق من واجهته وأعد فتحه وقارن النتائج. جهّز إصدارًا أقدم داخل VM أو snapshot مستقلة ببيانات اصطناعية، حدّثه إلى installer الحالي، وتحقق من عدم فقد/تكرار الفواتير أو القيود.
4. أزل التطبيق من Apps & Features، وتحقق من بقاء `%APPDATA%\RetailOS\data` والنسخ والمفاتيح وفق السياسة، ثم أعد التثبيت وتأكد من توفر البيانات. لا تختَر حذف بيانات مخصصًا إن ظهر.
5. شغّل اختبار Electron المعبأ بعد إتاحة استعلام هوية العملية أو اعتماد بديل أصلي مكافئ واختباره؛ لا تستخدم استثناءات ولا توقف عمليات غير مثبتة الملكية.
6. على Windows ثانٍ نظيف، انقل `.rfbackup` والمفتاح الحالي والمفاتيح السابقة المصدّرة عبر وسيط مشفر. استعد وقارن المستخدمين والصلاحيات والمنتجات والمخزون والفواتير والمرتجعات والمشتريات والموردين والمصروفات والخزينة والقيود وTrial Balance.
7. اختبر كلمة مرور خاطئة وملفات تالفة/ناقصة وفشل الاستعادة ثم إعادة التشغيل، واختبر طابعة حرارية وقارئ باركود فعليًا.

**الخلاصة: BLOCKED قبل Pilot.** أُغلق عائق عدم وجود build حالي؛ لكن تثبيت NSIS والترقية والإزالة والاحتفاظ وتشغيل Electron المعبأ وDPAPI/الاستعادة على جهاز آخر والطباعة الفعلية ما زالت غير مثبتة.

## خطة قبول Cross-Device على Windows 11 — مراجعة فقط، لم يبدأ النقل

**الحالة:** لم يتم تثبيت التطبيق على الجهاز الثاني، ولم يتم نقل أي ملف أو مفتاح، ولم يتم إنشاء backup رسمي من التطبيق في هذه المرحلة. تم التحقق من أن الفرع هو `fix/pre-pilot-hardening` والـ commit هو `a31f7ff0f9f184944ce7bb546880554e437efd93`، وأن SHA-256 للـ installer الحالي يطابق `C90EFFC39B1213501FC114BB6333D13BE661F323B22698D6397B0A092A36C717`. لم تُفتح قاعدة الإنتاج أو أي ملف userData.

### نتيجة مراجعة التشفير والتوافق

- صيغة `.rfbackup` تستخدم `AES-256-GCM`، ومفتاحها مشتق من عبارة المرور عبر `scrypt` بإعدادات `N=32768, r=8, p=1`؛ مع salt عشوائي 16 بايت وIV بطول 12 بايت ووسم GCM بطول 16 بايت (`packages/infrastructure/src/backup/sqlite-backup.service.ts:20-33, 36-57`). ملف النسخة نفسه يحمل salt/IV والوسم؛ فكّه يتطلب عبارة المرور الصحيحة فقط.
- **الخيار الموصى به للاختبار الأول:** تصدير يدوي من واجهة النسخ المشفر، بعبارة اختبار فريدة تُنشأ محليًا ولا تدخل التقرير أو المحادثة. تصميم هذا المسار لا يعتمد على DPAPI أو أي مفتاح محلي من الجهاز المصدر؛ عبارة النسخة كافية لفك التشفير (`apps/web/public/app.js:7689, 7931-7943`; `apps/web/server.mjs:5360-5376, 5380-5415`).
- **خيار النسخ اليومية:** يحتاج ملف النسخة اليومية مع المفتاح الحالي وكل المفاتيح السابقة المعروضة عبر `POST /api/backups/daily/key-export`. المسار يتطلب صلاحية النسخ ودور OWNER وإعادة إدخال كلمة مرور المالك، ويعيد المفاتيح السابقة وتعليمات الجهاز البديل مع `Cache-Control: no-store` (`apps/web/server.mjs:5137-5175`). سجل المفاتيح المحلي `daily-backup-keyring.bin` والمفتاح `daily-backup.bin` محميان بـ Electron `safeStorage`/DPAPI في userData (`apps/desktop/src/runtime.ts:297-363`)، فلا تنقل ملفي DPAPI إلى الجهاز الثاني ولا تعتمد عليهما هناك. التصدير هو المسار المدعوم لنقل مفتاح النسخ اليومية.
- `safeStorage` على Windows يعتمد على حماية DPAPI المرتبطة ببيانات دخول المستخدم نفسه؛ التطبيق لا يطلب `CRYPTPROTECT_LOCAL_MACHINE`. هذا النطاق لا ينتقل تلقائيًا لجهاز جديد. نطاق LocalMachine يتيح فك البيانات لأي مستخدم على نفس الجهاز، ولا يحل cross-device؛ لن نغيّر النطاق. [Electron safeStorage](https://www.electronjs.org/docs/latest/api/safe-storage)، [Microsoft CryptProtectData](https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptprotectdata).
- **قيود قبول مهمة:** الاستعادة إلى شركة بديلة تسمح باختلاف tenant ID فقط إذا كان الجهاز الهدف fresh، وتظل مطالبة بتطابق company code وcurrency (`packages/infrastructure/src/backup/sqlite-backup.service.ts:143-165, 218-247`; `apps/web/server.mjs:5403-5415`). القيم الافتراضية الحالية `STORE` و`EGP` (`apps/web/server.mjs:372-379`). لا تضف على الجهاز الهدف أي مبيعات أو مشتريات أو بيانات تشغيلية قبل الاستعادة. الحسابات والإعدادات في النسخة ستستبدل قاعدة الجهاز الهدف.

### الملفات المطلوبة لكل مسار

| المسار | ما يُنقل إلى Windows 11 | ما لا يلزم نقله |
|---|---|---|
| نسخة يدوية مشفرة (الموصى بها) | Installer الحالي بعد التحقق من SHA-256، ملف `.rfbackup` الذي نزّلته الواجهة، وعبارة المرور التي اختارها المالك محفوظة محليًا بطريقة آمنة ومنفصلة | `daily-backup.bin` و`daily-backup-keyring.bin` و`license-clock.dat` وملف قاعدة SQLite الخام أو مجلد `%APPDATA%` كاملًا |
| نسخة يومية مشفرة | Installer، ملف `.rfbackup` اليومي، المفتاح الحالي، وجميع المفاتيح السابقة اللازمة للنسخة؛ تُستخرج من الواجهة وتحفظ/تنقل خارج المحادثة | ملفات DPAPI المحلية، قاعدة SQLite الخام، أو مفاتيح غير مصدرة من سجل الجهاز المصدر |

لا تتضمن هذه الخطة أي قيمة حقيقية لعبارة مرور أو مفتاح. عند الموافقة والتنفيذ، تُدخل القيم مباشرةً في الواجهات المحلية فقط. لا تُرسل عبر بريد غير مشفر أو المحادثة.

### سيناريو البيانات الاصطناعية بعد الموافقة

1. تجهيز بيئة مصدر معزولة؛ لا تستخدم قاعدة متجر قائمة. إنشاء Owner اصطناعي وبيانات اعتماد اختبارية لا تظهر في التقرير.
2. إنشاء فئة ومنتج بمتغيرات لون/مقاس وكميات مختلفة، ثم مورد وفاتورة شراء ومدفوعتها.
3. تسجيل بيع وإصدار فاتورة، ثم مصروف اصطناعي، والتحقق من المخزون وحسابات النقد/الدفع والقيود وميزان المراجعة.
4. من شاشة النسخ الاحتياطي الرسمية: تصدير يدوي مشفر بعبارة محلية فريدة، ثم تسجيل مكان الملف فقط دون تسجيل العبارة. هذا المسار يتجنب نقل مفاتيح DPAPI.
5. على Windows 11 مستقل: التحقق من SHA-256 للـ Installer قبل التثبيت، التثبيت per-user، والإعداد الأولي بشركة لها company code وcurrency مطابقان للمصدر. يجب إبقاء الهدف fresh بلا عمليات تشغيلية.
6. رفع ملف `.rfbackup` من شاشة الاستعادة، إدخال العبارة محليًا، وتأكيد الاستبدال. بعد إعادة التشغيل، تسجيل الدخول بحساب Owner الاصطناعي الموجود في النسخة المستعادة.
7. مقارنة المستخدمين/الأدوار، المنتجات والمتغيرات والكميات، فواتير الشراء والبيع وتفاصيلها، المصروف، الرصيد النقدي، القيود وTrial Balance. تحقق من `integrity_check = ok` و`foreign_key_check` بلا صفوف، ومن عدم وجود قيود يتيمة أو فروق مخزون أو معاملات مكررة.
8. إذا اخترنا النسخة اليومية بدل اليدوية، صدّر المفتاح الحالي وجميع المفاتيح السابقة بعد إعادة مصادقة المالك، وانقلها مع `.rfbackup` عبر وسيط مشفر. لا تبدأ هذا المسار قبل الموافقة الصريحة على نقل الأسرار يدويًا.

### ما ينتظر الموافقة/التدخل اليدوي

- إنشاء البيانات والنسخة عبر التطبيق الرسمي غير منفذ؛ بيئة المصدر الحالية لا تملك تثبيت RetailOS مؤكدًا، واختبار تشغيل `win-unpacked` ما زال يتوقف fail-closed قبل التشغيل بسبب CIM. لن أتجاوز الحارس لتوليد النسخة.
- لا تثبيت على الجهاز الثاني ولا نقل Installer أو backup أو مفاتيح تم حتى الآن.
- الـ Installer غير موقّع Authenticode. تحقق SHA-256 يثبت مطابقة الملف المعروف هنا، لكنه لا يثبت هوية ناشر موقّعًا؛ ينبغي أن يطابق مالك الجهاز البصمة يدويًا قبل التثبيت، وقد يعرض Windows تحذيرًا.
- حتى بعد اجتياز الاستعادة اليدوية، لا يُغلق قبول النسخ اليومية/DPAPI إلا إذا تم اختبار المفتاح اليومي المُصدّر فعليًا على Windows 11 مستقل. نجاح الاختبار اليدوي لا يُستنتج من CI أو من محاكاة DPAPI.
- لا تغييرات كود أو تشفير، ولا commit أو push أو merge في هذه المرحلة.

**حكم Cross-Device الحالي: التوافق مدعوم تصميميًا للنسخة اليدوية بعبارتها، ومدعوم تصميميًا للنسخ اليومية بمفتاحها المصدّر؛ لكن لا يوجد قبول عملي على الجهاز الثاني بعد. الحالة تظل BLOCKED حتى تنفيذ السيناريو ومقارنة البيانات فعليًا.**
